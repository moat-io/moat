# Create a new empty Alembic migration

Generate a new **empty** Alembic revision so the user can hand-write the
`upgrade()` / `downgrade()` bodies. This deliberately does **not** use
`--autogenerate` — the migration is created blank.

## Steps

1. **Get a migration message.** If the user gave a description of the change,
   use it as the `-m` message. Otherwise ask them for a short description
   (e.g. `"add index on principal.user_name"`). Keep it concise — Alembic
   slugifies it into the filename.

2. **Create the revision.** Run from the repository root
   (`/Users/joel/working/moat`):

   ```bash
   export PYTHONPATH=./moat/src
   export CONFIG_FILE_PATH=moat/config/config.yaml
   ./venv/bin/alembic -c moat/alembic.ini revision -m "<message>"
   ```

   Notes:
   - **Use `./venv/bin/alembic`, not bare `alembic`.** Alembic is only
     installed in the repo's `venv/` and is **not** on `PATH` — running
     `alembic` directly fails with `command not found: alembic`. If `venv/`
     is missing, create it and install deps with
     `python3 -m venv venv && ./venv/bin/pip install -r requirements.txt`.
   - **No `--autogenerate`** — this keeps `upgrade()`/`downgrade()` empty.
   - `env.py` imports `database` and `models`, so `PYTHONPATH=./moat/src` is
     required or the command fails on import.
   - `CONFIG_FILE_PATH=moat/config/config.yaml` is also required by the
     imports; omitting it fails on config load.
   - Alembic auto-wires `down_revision` to the current head, so revisions
     chain correctly without manual edits.

3. **Report the new file.** The command prints the path of the generated file
   under `moat/src/alembic/versions/`. Read it back and show the user the
   `revision` / `down_revision` identifiers and the empty `upgrade()` /
   `downgrade()` stubs so they know where to add their logic.

4. **(Optional) Fill in the migration.** If the user described the schema/data
   change, offer to implement the `upgrade()` and `downgrade()` bodies. Use
   `op.execute(...)` for raw SQL. Two reference migrations:
   - `e1833e19df8b_history_table_functions_and_triggers.py` — functions and
     triggers with dialect branching (`postgresql` vs `mysql`).
   - `180d97518271_postgres_record_updated_date_triggers.py` — a
     **Postgres-only** migration: it early-returns when
     `op.get_bind().dialect.name != "postgresql"` so it's a no-op on other
     dialects, and both `upgrade()` and `downgrade()` guard the same way.

   To make a migration apply only for a specific database, branch on
   `op.get_bind().dialect.name` (values: `"postgresql"`, `"mysql"`,
   `"sqlite"`) in both `upgrade()` and `downgrade()`.

## Applying the migration

Creating the revision does not run it. To apply:

```bash
export PYTHONPATH=./moat/src
export CONFIG_FILE_PATH=moat/config/config.yaml
./venv/bin/alembic -c moat/alembic.ini upgrade head
```

Only run `upgrade head` if the user asks — creating the revision is the
primary job of this skill.
